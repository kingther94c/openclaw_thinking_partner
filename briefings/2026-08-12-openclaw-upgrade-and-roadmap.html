New upstream capability worth knowing

The jump brings a Skill Workshop lifecycle curator and a /learn command that drafts skills from recent work. Relevant to us because market_helper deploys machine-generated skills: the curator only touches skills created through Workshop proposals, so our generated mh-* files are not subject to auto-archiving. The real hazard is the reverse — if anyone uses /learn or Workshop to edit an mh-* skill, the next exporter run silently overwrites it.

One root cause behind all three proposals

the capability exists inside; the sanctioned path cannot reach it

Reading how market_helper actually integrates surfaced a consistent pattern. Every capability the consumer needs already exists inside the gateway — but only behind the CLI or the operator RPC surface. Our own integration-kit/boundaries.md tells consumers to use the HTTP API and never touch ~/.openclaw. Since the sanctioned path cannot reach these capabilities, the consumer reaches around it instead — and our stated boundary is, today, aspirational rather than real.

Three developments

ordered by how much reach-around each one removes

01

A real consumer provisioning path

Make our stated boundary enforceable by giving consumers a supported way to do the three things they currently do by editing the provider's files.

Evidence
  • Our kit forbids exactly what the consumer must do: "Do not modify this repo, the ~/.openclaw config, agents, or SOUL.md from your project." integration-kit/boundaries.md
  • The consumer reads the provider's config file to recover the bearer token, with a fallback chain ending in _openclaw_config_token(). market_helpertrade_advisor/ai/gateway.py:104
  • A deploy script copytrees mh-* skill dirs into the managed ~/.openclaw/skills, then prints that allowlists must be set by hand in ~/.openclaw/openclaw.json. market_helperscripts/dev/deploy_openclaw_skills.py
  • The agent→skill map is a hand-maintained mirror of the provider's allowlist — two sources of truth that can drift with no guard. market_helpertrade_advisor/ai/skill_export.py:106
Proposal

Two of these are already solvable with shipped upstream features that our kit never mentions. skills.load.extraDirs can point straight at the consumer's version-controlled skill dir, which deletes the copy step and the whole deploy script. openclaw skills install ./path --agent <id> already scopes a skill to an agent. Document both in the kit as the supported path, then close the genuine remaining gap: allowlist mutation and token issuance still have no answer other than editing config by hand.

Quick win available now Mostly docs + config Removes 1 script entirely
02

A skills.resolved method, so delivery is provable

Replace a flaky model-probe with a deterministic answer to "which skills does this agent actually carry right now?"

Evidence
  • To prove skills reach the model, the consumer asks each agent to quote an unguessable marker verbatim and greps the reply. Its own docstring concedes it is a "best-effort smoke tool, NOT a CI gate", is "run-to-run flaky", and that a negative result "is inconclusive". market_helperscripts/dev/verify_openclaw_skills.py
  • The resolution logic already exists — it is simply CLI-only: skills list --agent <id> --json, skills check --agent <id>, skills info <name> --agent <id>. docs/cli/skills.md:54,57,59
  • The gateway already exposes a scoped skills.* RPC namespace (skills.curator.status at operator.read, proposals at operator.admin) — but nothing returns per-agent resolved skills. docs/tools/skill-workshop.md:273
  • A sibling project shows the cost of not having digests: its generated skill mirror "drifted twice" before a comparison guard was added. RE_searchtools/sync_agents_skills.py
Proposal

Add skills.resolved at operator.read, returning each agent's resolved skill names plus a content digest per skill body. This is additive into an existing namespace at an existing scope, reusing the resolver the CLI already calls — not a new subsystem. It converts the probe script into a real CI gate, and it proves isolation too (an agent must not carry skills outside its allowlist). The digest is a bonus: it lets any consumer that generates skills verify the deployed body matches what it generated, which is the drift guard two of our projects each built by hand.

Additive, existing namespace Small surface Turns a flaky probe into a gate
03

Quota headroom on the consumer surface

The gateway already knows the remaining quota. The consumers that need it most are the only ones forbidden to ask.

Evidence
  • usage.status "returns provider usage windows/remaining quota summaries" and is already scoped at operator.read. docs/gateway/protocol.md:347 · src/gateway/methods/core-descriptors.ts:38
  • But our kit tells consumers not to depend on gateway server-methods, so the sanctioned path cannot see it. Quota coordination is left as a human protocol: "check quota with the owner", "coordinate with the owner rather than retrying in a loop". integration-kit/operations.md · boundaries.md
  • This shifts from theory to pressure as projects multiply: three dashboard panes already route to three separate agents, with no client-side caching of advisories on the call path. market_helperdashboard/pages/trade_advisor/modules/{tactical,option,fx_hedge}.py
  • All of it lands on one personal ChatGPT subscription with rolling limits — a constraint our own boundaries doc flags but gives no mechanism to respect. integration-kit/boundaries.md — "Quota & rate"
Proposal

Expose read-only headroom on the path consumers are actually allowed to use, so a client can self-throttle or degrade deterministically instead of discovering the limit as a refusal. The cheapest honest version is a documented, token-gated read that mirrors usage.status — the work is the exposure decision and the contract, not new accounting. Pair it with a note in the kit on caching by input hash, which the boundaries doc already recommends and no consumer currently implements on the advisor call path.

Data already exists Needs a scope decision Scales to 5 sibling projects
